# 製品コードのレビューと対応記録

対象は `a01e0da` の静的サイト生成、読書画面、テスト、配布経路。記事の文章は対象外とした。以下の再現手順と原因は修正前のコミットに対応する。A〜Eの修正と検証は[対応記録](#対応記録)にある。

## 構造と指摘の位置

| 層 | 入力から出力まで | 表面に出る問題 | 原因の所在 |
| --- | --- | --- | --- |
| 1. 閲覧操作 | 目次を選ぶ → 折りたたみ・位置・フォーカス・履歴を更新 | 1段ではURLが目的の節を指していてもその節を読めない | 移動先を表示可能にする処理がn段の移動処理だけにある（C） |
| 2. ページ生成 | 変換済み本文と目次を `[slug].astro` に組み込む | 数式の目次項目は見えるがリンクが先頭を指す。サイト内の相対リンクが別タブを開く | 見出しの表示と識別子の入力が異なる（B）。リンクの内外は文字列の先頭だけで決めている（D） |
| 3. 入力の変換 | `lib/post.ts` → 独自記法の前処理 → MathJax・remark/rehype → HTML | コード例に内部表現が現れ、続く本文の区切りも失われる | Markdownの構文境界を決める前に、同じ文字列へ独自記法の置換を施している（A） |
| 4. 検証・配布 | 静的HTMLの検査 → 実ブラウザーの操作 → Pagesへ配布 | 対象外のブラウザーを指定しても検査が成功扱いになる | ブラウザー名を絞り込んだ結果と実行対象を照合していない（E） |

段組み本体には、論理座標（`column-coordinates.ts`）、ブラウザーが扱えるスクロール範囲への変換（`column-geometry.ts`・`column-viewport.ts`）、原本を計測して画面内の段へ複製する処理（`column-fragments.ts`）に境界がある。今回の目次の問題はその外側にある。A〜Eはいずれも座標系や段の複製方式を入れ替えずに直せる。[段組みの実装](column-layout.md)

## 修正の順序と受け入れ条件

最新のmain上で各項の入力を先に試し、同じ症状がある項から着手する。既に直っていれば、対応する変更または動作確認を記録して次へ進む。A、B、C、D、Eの順で独立したPRにできる。各PRはmainから分岐し、後続PRが先行PRのマージを前提にしなくて済むよう差分を絞る。テストには合成入力を使える。再現用の記事を公開対象の `post/` に加える必要はない。

### A　コードの内容と終端を保つ（最優先）

- **再現**　次の入力を本番ビルドすると、コード内の `$x$` は数式用の空のspanを表す文字列へ変わり、終端フェンスはその直後に連結される。後続の見出しと本文まで同じ `pre` に入る。また通常のバッククォート3個のコードフェンス内でも、HTML例の `<summary>{'abc'}</summary>` が `<summary>abc</summary>` に変わる。
- **根本原因**　`preprocessMarkdown` のコード退避は決まった長さのバッククォートだけにマッチする。さらにsummaryの旧記法変換は退避より前に全体へ適用される。後段の数式直後の改行除去が、フェンスの直前にも作用する。[前処理](../lib/preprocess.ts)
- **変更**　最初にコードの範囲を識別し、その内容を旧記法・数式・脚注などの置換から保護する。既存のremarkパーサーが返す code / inlineCode のソース位置を利用する案を、一時記事で試す。フェンスの情報文字列に施す言語・ファイル名の変換は独立して残す。入れ子のリストや引用で字下げ・行頭記号まで失わないことを確認する。
- **完了**　下例のコードをコピーすると元の式が得られ、「後続」は独立した見出しとして目次から開ける。チルダ、内側に短いフェンスを含む長いバッククォート、通常のHTMLコード例、コード外の数式と旧記法summaryを比較する。単体の前処理を扱う既存ファイルはないため、この再発を捉える最小の `lib/preprocess.test.ts` を追加してよい。最終HTMLは本番ビルドで確認する。

````markdown
~~~txt
$x$
~~~

## 後続

本文
````

### B　目次に載る見出しに到達可能なIDを付ける（高）

- **再現**　合成記事に `## $x$` と `## $y$` を順に置く。本番ビルドで最初は `<h2 id="">` と目次の `href="#"`、次は `id="-1"` になった。最初のリンクからその見出しを指定できない。
- **根本原因**　数式が空のプレースホルダーになっている時点で `rehypeSlug` がテキストからIDを作る。後の `rehypeToc` は空文字列も採用し、表示には別途組版済みの数式を使う。通常のリンク検査ではページ先頭を指す `#` は正当なので通る。[変換順](../lib/convert.ts)・[目次の生成](../lib/toc.ts)・[目次リンク](../src/components/TocList.astro)
- **変更**　既存の非空IDと明示IDは維持し、目次に載せる見出しでIDが空のものに決定的な代替IDを付ける。後続の見出しや見出し以外の明示IDを含め、同じページのIDと衝突しないようにする。本文とすべての目次で同じIDを使う。
- **完了**　上例の各リンクで別々の見出しに到達し、フラグメント付きで再読み込みできる。通常の見出し、重複、既存の明示IDのリンクも有効。既存の `tests/links.test.mjs` を広げるなら「目次リンクが同じ記事の実在する見出しを指す」を検査する。一般の `href="#"` を一律エラーにしない。合成入力でも修正前に失敗することを確かめる。

### C　閉じた節への移動で見出しを表示し、フォーカスを渡す（高）

- **再現**　閉じた `<details><summary>開く</summary>` の中に空行を挟んで `## target` を置く。1段のサイドバー目次で target をEnterで選ぶ。ChromiumとFirefoxの双方で `location.hash` は `#target`、本文の `details.open` はfalse、見出しはフォーカスを持たなかった。
- **根本原因**　1段の目次は既定のフラグメント移動をキャンセルし、自前で座標を読み、最後に履歴とフォーカスを更新する。座標を読む前に移動先の祖先を開く処理が欠けている。n段の `navigate` は先に祖先を開き、複製を同期し、計測してから移動する。[1段の移動](../src/components/Toc.astro)・[n段の移動](../src/scripts/column-layout.ts)
- **変更**　祖先の折りたたみを開く小さな処理を両経路で使い、座標取得より先に実行する。n段の再計測・複製同期はそのままn段側が受け持つ。本文の折りたたみと、選択時に閉じるモバイル目次を区別する。
- **完了**　`tests/toc.browser.test.mjs` のキーボード移動のケースを広げ、移動先を閉じた折りたたみの内側に置く。通常と動きを減らす設定で、選んだ節が見え、見出しにフォーカスがあり、次のTabでその後の本文へ進める。入れ子の折りたたみ、モバイル目次の閉鎖、履歴を増やさない挙動を確認する。

### D　記事リンクの開き方を宛先に合わせる（中）

- **再現**　ビルドした記事中の `[同じサイト](../example/)` に `target="_blank"` が付き、`[外のサイト](//example.org/path)` には `target` も `rel` も付かなかった。どちらも行き先自体はあるため、リンク切れ検査では分からない。
- **根本原因**　`rehypeSafeLinks` がスラッシュまたは `#` で始まるかを判定している。相対表記とオリジンの違いをこの判定で表すことはできない。[本文リンクの変換](../lib/convert.ts)
- **変更**　公開サイトのURLを基準にHTTP(S)の宛先を解決して内外を決める。サイト設定を再利用し、本文変換のキャッシュが本文だけをキーにしている点に注意する。内外の判定にページごとの絶対パスは必要ない。空hrefの一覧への補正、ルート相対パスへのbase付与、明示属性、mailto等の既存の扱いを独立に確認する。
- **完了**　相対・同一オリジンの絶対URL・フラグメントは通常の同一タブ移動、外部HTTP(S)はスキームを省いた場合も既存の新規タブとrelの規則に従う（著者がtargetを指定していない場合）。小さな変換例で確かめ、既存の本文内リンクの履歴試験を通す。

### E　ブラウザーを実行していない検査を成功扱いにしない（検証基盤）

- **再現**　mainで `TEST_ENGINES=webkit node --test tests/column-ordinary-navigation.browser.test.mjs` を実行すると、対象エンジンが空でも正常終了する。既定のCIはChromium・Firefoxを指定できる状態で実行している。この問題はローカルの選択やCIの将来の指定変更で表れる。
- **根本原因**　`tests/browser.mjs` は指定名を対応エンジンの一覧でフィルターするだけで、空集合や未知名を通知しない。その結果をループしてテストを登録するファイルでは、操作を一度も検証しない。[エンジン選択](../tests/browser.mjs)
- **変更と完了**　指定した名前をtrimし、未対応の名前が一つでもあれば、その値と選べる名前を示して失敗させる。未指定・単独・カンマ区切りの有効な選択と、誤記・既知名と未知名の混在をコマンドで確認する。WebKit対応の作業状況は [ロードマップ](../ROADMAP.md) で確認する。

## GitHub Pagesの配布

browserジョブで一度ビルドし、リンク検査とブラウザー検査を通過した同じ `dist/` を配布に使う。`main` へのpushと手動実行ではbrowserジョブが成果物を渡し、deployジョブは型・単体テストとbrowserジョブの成功を待って公開する。PRでは型・単体・リンク・ブラウザー検査を実行する。[配布workflow](../.github/workflows/deploy.yml)

## 後続セッションの検証と引き渡し

1. リポジトリの `AGENTS.md` に従い、該当箇所と既存テストを先に確認する。修正前に失敗する観測点は、Aならコピー元の文字列と後続の見出し、B・Cならリンク先の実体とフォーカス、Dならリンクを開くタブ、Eならコマンドの終了結果。
2. 各PRで `npm run astro -- check`、`npm test`、`npm run build`、`npm run test:links` を実行する。ブラウザー確認には本番ビルドのpreviewを使い、`TEST_BASE_URL` をそのサーバーのbase付きURLに合わせる。まず該当ファイルを `node --test tests/<対象>.browser.test.mjs` で実行し、PRのCIで全体を確認する。
3. 受け入れ条件を満たした項、追加したテストで初めて検知できる不具合、実行結果をPRに残す。既存PRへ追記するときは状態を確認し、マージはそのPRについてのユーザー指示を待つ。任意提案の着手は対応する課題が生じたときに判断する。

レビュー時点では型検査、単体テスト、本番ビルド、生成物のリンク検査が成功した。上記のブラウザー再現は一時ビルドに対する個別確認。全ブラウザースイート、Safari実機、支援技術での読み上げ、速度計測は今回の検証範囲外。
