## 別文書での幾何学計測の予備実験

同サイズの画面外 iframe に記事を読み込み、n 段初期化とフォント読み込み後に、本文直下と `.post` 直下の要素 40 個の位置・大きさを保存した。もう一つの iframe で同じ要素を計測すると、最大差は両ブラウザーで 0 px。先の iframe のロードから準備完了まで Chromium 418 ms、Firefox 1022 ms。保存した JSON はそれぞれ約 1.0 KB、1.3 KB。両 iframe は同時に存在するため、先読み 1 件あたりのメモリ増加量は未測定。

この実験は別文書への値の受け渡し可能性を調べただけで、`ReadingFragments` の全計測値の移植や実際の描画への再利用を行っていない。事前にレイアウト済みの要素を読み直す時間は、初期レイアウトの処理時間ではない。先読みの効果、CPU 時間とメモリ負荷の定量化、フォント・画像・サイズ・履歴の状態変化時の無効化、および先読みが使えない場合の1段表示防止は未検証。

## 断片計測値の移送試作

実験用の `ReadingFragments` 拡張で計測結果を、要素パスと各矩形・余白の折り畳み深さとしてシリアライズし、別文書の要素に結び直す試作を追加した。`node scripts/reading-fragment-snapshot-experiment.mjs` を開発サーバーに対して実行し、先読み側と遷移先に相当する二つのページで比較した。1440×900 の `symmetric-polynomial` で、両ブラウザーとも全矩形の最大差は 0 px、5 箇所の描画断片の HTML は一致し、先頭要素を追加した DOM への復元は拒否された。保存サイズは Chromium 5,176 バイト、Firefox 5,436 バイト。

この API は遷移処理にはまだ接続されていない。パスとタグ名だけでは、末尾要素の追加や同じタグ内の文章変更、フォント、画像、幅、ブラウザーズーム、開閉状態などによる計測値の無効化を判定できないため、実際の利用には追加の検証が必要。

ページが既にレイアウトされた状態では、断片の再計測は Chromium 約 0.9 ms、Firefox 約 3 ms、復元はそれぞれ約 0.3 ms、0 ms（時計の分解能内）だった。幅を変更してレイアウトを無効化した後、元の幅に戻してレイアウトまで行う比較では、再計測が 2.3 ms / 5 ms、復元とレイアウトが 1.8 ms / 2 ms。これは一例であり、初回ページ構築の全コストではない。

別途、開発サーバーで初期化関数を一時計測したところ、初回 `measure()` は Chromium 187〜210 ms、Firefox 192〜236 ms。そのうち `ReadingFragments.measure()` は両者で 0〜1 ms、本文のサイズ取得までが約 89〜120 ms、最初の段の構築・配置が約 82〜119 ms だった。したがって、断片計測値だけを先読みしても、この待ち時間の大部分は残る見込み。計測用の一時コードは取り除いた。

## ページ全体の画面外準備の負荷

`scripts/reading-preload-memory-experiment.mjs` で、一覧だけの状態と 1 件の画面外 iframe の準備後を比較した。ビルド済みページ、上記と同じ記事・画面サイズの各 1 回の例では、準備までの経過時間は Chromium 548 ms、Firefox 586 ms、ブラウザー子プロセスの RSS 合計の差はそれぞれ約 126 MiB、69 MiB だった。RSS 合計は共有ページの重複やプロセスの起動・キャッシュを含む粗い上限的指標であり、実使用メモリの純増ではない。別の各 1 回で、準備開始前から準備 500 ms 後までの全ブラウザー子プロセス CPU 時間差は両者とも約 1 秒だった。ただし `ps` の秒単位の累積値とプロセス生成・終了を含む粗い測定で、先読みだけの正確な CPU 時間ではない。記事ごとにブラウザー文書全体を常駐させる案は、実際の遷移時間短縮とメモリの精査なしに採用できない。

## 初期表示の暫定対策

JavaScript が有効な場合、記事の初期モードと履歴位置が確定するまで本文を非表示にする。通常の先読みが未完了でも1段本文を一瞬見せないための処理であり、段組み準備の先読みではない。Chromium と Firefox で一覧からの遷移、直接アクセス、1段・n段、JavaScript 無効時を検証した。初期化が 10 秒以内に終わらない場合は、本文を利用できるよう1段表示へ退避し、後から初期化が完了しても自動的に n 段へ切り替えない。

## 同一文書での段組み準備と遷移時の引き継ぎ試作

一覧の文書に、画面外・操作不可の領域を一つ作り、取得した記事 HTML の本文を配置して段幅・本文長・断片を計測、先頭付近の断片を構築した。`scripts/reading-in-document-experiment.mjs` は、この計測値と断片を実際の記事画面のものと比較する。`scripts/experiments/prepared-dom.patch` は調査専用の一時パッチで、計測済みの本文、`ReadingFragments`、断片を Astro の差し替え前に遷移先へ移す試作。パッチを適用した開発用またはビルド済みページに `scripts/experiments/reading-prepared-dom.mjs` を実行した後、必ずパッチを戻す。この試作には無効化、履歴復元、記事内操作などの実装がなく、本番用ではない。

1440×900 の数式記事では、画面外と遷移先の各矩形の最大差は Chromium 0 px、Firefox 約 0.00025 px、先頭から 3 段分の断片は完全一致した。390×844 のコード記事 `tips-python` では位置は一致したが、事前生成された断片には記事表示後に追加されるコピーボタンがなく、HTML は一致しなかった。ボタン類を除くと一致する。このため、既存の記事装飾・操作の初期化と先読みを統合しなければ、そのまま引き継ぐことはできない。

ビルド済みページで、先読みなしと、先読み済みの本文・計測・断片を実際の遷移へ引き継ぐ処理を交互に各 3 回実行した。クリックから本文の非表示解除までは以下の通り（ms）。最初の n 段領域のスクリーンショットは各ブラウザー内の先読み前後で一致した。

- Chromium: 先読みなし 569、498、595 ／ 引き継ぎ 399、375、374
- Firefox: 先読みなし 552、5270、9292 ／ 引き継ぎ 375、354、372

初回 `measure()` 内だけの時間は、Chromium で 238〜261 ms が 212〜239 ms、Firefox で通常 183〜200 ms が 180〜195 ms（先読みなしの 1 回は 5136 ms）だった。Firefox の先読みなしでは複数秒の外れ値が発生したため、環境依存のばらつきが大きく、上記から一般的な速度改善を推定することはできない。

数式用の CSS と数式 DOM を一度読み込み、フォント等を温めてから破棄する対照を、準備なし・段組み引き継ぎと交互に各 2 回比較した。クリックから表示可能までの時間は、Chromium が準備なし 943、539 ms、数式の事前読み込み 358、377 ms、段組み引き継ぎ 367、374 ms。Firefox は準備なし 626、8721 ms、数式の事前読み込み 461、441 ms、段組み引き継ぎ 370、349 ms。この対照はフォント取得だけではなく数式 DOM の構築・レイアウトも含む。計測済み段組みの移送による追加の効果は、少なくとも Chromium のこの条件では確認できず、Firefox でも数十 ms にとどまる。差し替え後にブラウザーがレイアウトを再度行うことが主な制約と考えられる。

準備時の負荷もビルド済みページで測定した。数式記事の一例では準備の経過時間が Chromium 865 ms、Firefox 586 ms。ブラウザー子プロセスの PSS 合計差は約 126 MiB、84 MiB、CPU 時間の差はそれぞれ 0.59 秒、1.55 秒だった。PSS は共有メモリを按分するが、フォント・キャッシュ・新規プロセス等も含み、準備した DOM 単独の使用量ではない。CPU は `/proc` の累積値からの差で、別のブラウザー処理も含む。コード記事・390×844 の一例では準備時間が 82 ms、89 ms、PSS 差が約 11 MiB、24 MiBで、記事の内容により負荷は大きく異なった。

この段階では、数式記事に対する段組み DOM の引き継ぎを実装に採用していない。負荷に対する追加効果が小さく、本文の操作追加やフォント・画像・画面寸法・履歴状態の検証が必要なため。候補としては、画面外での全文レイアウトを避けて必要なリソースを先に取得する方法、または画面外の描画をページ差し替えで再レイアウトさせずに保持する方法を調べる必要がある。いずれも現時点では、実用的な n 段準備の先読みとして完成していない。

### 主フォントだけの先読みとの比較

上記の対照は数式 DOM 全体のレイアウトを含むため、記事 HTML の `link rel="preload"` で指定されるフォント 1 件だけを事前取得する比較も行った。クリックから表示可能まで、Chromium は準備なし 1525、587 ms、フォント 1 件 494、554 ms、段組み引き継ぎ 371、473 ms。Firefox は準備なし 10869、13442 ms、フォント 1 件 9702、11840 ms、段組み引き継ぎ 507、380 ms。Firefox の測定環境では先読みなしとフォント 1 件の条件で繰り返し複数秒の停止が発生し、一般的な改善量を示すデータではない。フォント 1 件の取得だけでは、少なくともこの環境における Firefox の停止を回避できなかった。

比較スクリプトは既定で準備なし、フォント 1 件、段組み引き継ぎを各 2 回測る。数式 DOM を使った比較は `RM_MODES=none,fonts,prepared,none,fonts,prepared` で再現できる。ビルド済みページで測るには、パッチ適用中にビルドし、`scripts/experiments/reading-fragment-snapshot.ts` を実験用に ESM バンドルして静的サーバーから配信する必要がある。

## 組み立て済みの画面を保持して先に表示する試作

準備済み DOM を差し替える際の再レイアウトを避けるため、別文書の iframe に完成済みの記事画面を置いて保持する方式と、一覧文書の画面外に段・目次・背景を組み立てて保持する方式を試した。どちらも一時的な重ね表示で、実際の記事の初期化完了後に取り除く。実装本体には組み込んでいない。

ビルド済みの数式記事、1440×900、各 1 回の例で、クリックから重ね画面の 2 回目のアニメーションフレームまで、iframe は Chromium 31 ms、Firefox 24 ms、同一文書の画面はそれぞれ 36 ms、55 ms だった。これは描画完了の厳密な時刻ではないが、スクリーンショットでも段組みの本文を確認した。表示後に遷移先の準備を意図的に 1.2 秒遅らせた試験でも、差し替え前に段組みが見えた。同一文書の方式では、差し替え前の画像に Chromium で約 1 万画素、Firefox で約 3 千画素の差が残った（全 129.6 万画素中、最大色差はそれぞれ 43、36）。背後の記事を一時的に隠すと、差し替え後の画像は両ブラウザーとも一致した。画面外準備中の一覧画像も差はなかった。

コストは大きい。別文書を使う例では先読み完了まで Chromium 679 ms、Firefox 3046 ms、先読み後の PSS 差は約 139 MiB、58 MiB だった。実際の記事も作られ両画面が共存する時点の PSS 差は約 292 MiB、210 MiB。PSS はブラウザー全子プロセスとフォント・キャッシュ等を含み、重ね画面単独の消費ではない。同一文書の方式でも数式記事の先読み後は約 96 MiB、60 MiB 増えた例がある。一方、コード記事 `tips-python` の例は iframe 方式で約 21 MiB、9 MiB の増加で、記事の内容によって負荷が異なる。各数値は 1 回のローカル試験である。

iframe の画面を操作可能にすると、初期試作では表示中にスクロールした位置が切り替え時に失われた。`restore-preview-position.patch` の一時試作で論理位置を移送すると、両ブラウザーで位置と画面が一致した。さらに詳細の開閉状態を移さない場合は開いた詳細が閉じてしまったため、`restore-preview-details.patch` では開閉状態を移し、再計測した段組みが一致する場合に位置を復元した。詳細を開いてスクロールした 1 条件では両ブラウザーで開閉状態と位置が一致し、画像差は Chromium で最大 7、Firefox で 0 だった。内容の更新、フォント・画像の遅延、リサイズやズーム、フォーカス、選択、内部スクロール、目次やリンク、画面切り替え中の入力、位置の範囲などは検証・実装していない。

もう一つの重大な問題として、親画面で記事への遷移が進行中に iframe 内の「閉じる」を押すと、iframe だけが一覧へ移り、親は記事を開き続けることを Chromium で確認した。スクロール位置の移送だけでは履歴や操作の整合性を保てない。スクロールした一覧から開いて親で履歴を戻す限定試験では、Chromium と Firefox とも一覧の 442 px の位置は維持されたが、この試験は上記の競合を解決するものではない。

試作の実行には `scripts/experiments/reading-retained-frame.mjs` と `scripts/experiments/reading-retained-layer.mjs` を使用した。後者は `scripts/experiments/retained-modules.ts` の ESM バンドルを必要とする。遷移を遅らせる試験には `RM_DELAY=1`、iframe を操作して引き継ぐ試験には `RM_INTERACTIVE=1 RM_HANDOFF=1` を指定し、対応する一時パッチをビルド前に適用・ビルド後に戻す。これらのパッチは検証用であり、入力値と記事状態の検証が不十分なため適用したまま運用してはならない。

実際に利用できる先読みには、ページ切り替えと操作を一つの履歴に統合し、準備を中止・破棄するタイミングとメモリ上限を決める必要がある。速く見えるだけの読み取り専用プレビューを完成とは扱わず、現段階では採用していない。

## 先読み済み iframe を記事そのものとして使う試作

二重に記事を作る代わりに、親側のページ差し替え時に本文と記事ヘッダーの生成を取り除き、先読み済み iframe をそのまま表示・操作する方式も試した。`scripts/experiments/reading-retained-reader.mjs` と `forward-preview-navigation.patch` は検証専用で、本体には未接続。後述の履歴試験には `reload-frame-history.patch` も必要である。

900×500 の `tips-wsl` で、Chromium と Firefox の両方で iframe 内をスクロールでき、親の URL が記事を指し、親側に記事本文が二重生成されないことを確認した。ブラウザーの「戻る」と iframe の「閉じる」から一覧に戻る試験では、442 px の一覧位置と記事リンクへのフォーカスが維持された。記事への遷移がまだ完了していない間に iframe の「閉じる」を押した場合も、親側の遷移を中止し、同じ位置とフォーカスへ戻せた。準備済み iframe にフォーカスを渡す試作では、両ブラウザーで矢印キーによる段移動もできた。

初期試作では一覧に戻ってからブラウザーの「進む」を押すと読書位置が失われた。iframe の履歴キーを親へ共有し、読み直し時にセッション保存値を再取得すると Chromium では復元できたが、Firefox は iframe を外す間にネイティブスクロール値が変化し、誤った位置が保存された。取り外し直前に試験用に iframe の読書処理を終了させると、両ブラウザーで縦横の論理位置を復元できた。この終了は内部イベントを人工的に発火する実験であり、そのまま本番で使用すべきものではない。

目次操作では iframe のハッシュだけが変わり、親のアドレス欄は変わらなかった。iframe 内の `history.replaceState` を親へ反映する試作では、両ブラウザーで目次の URL が一致し、戻る・進む後も位置とハッシュが復元された。ただしネイティブなハッシュ移動、`pushState`、子フレームによる履歴項目の増減は未解決。別記事への通常リンクも初期試作では iframe だけが移動したが、リンクを親の Astro ナビゲーションへ転送する試作では、両ブラウザーで親の URL が移動し、戻ると元の記事の位置が復元された。外部リンク、別タブ、ダウンロード、転送中の操作は未検証である。

1440×900 の数式記事における各 1 回の PSS 概算は、通常の記事表示で一覧時より Chromium 約 170 MiB、Firefox 約 133 MiB 増、先読み iframe を記事として使う場合は約 204 MiB、199 MiB 増だった。別プロセスのキャッシュやフォント等を含む粗い測定であるが、記事の二重生成を避けても追加負荷は残る。開く前の先読み時点でも PSS が増えるため、同時に保持する記事数、開始条件、取り消しや破棄、低メモリ端末への配慮を決める必要がある。

印刷にも制約が見つかった。Chromium の通常記事は 6 ページだった `tips-wsl` が、iframe を親から印刷すると 1 ページに切れた。印刷時だけ iframe の本文を親へ複製する試作では両者とも 6 ページ、抽出文字数も同じになったが、数式記事では通常 10 ページに対し複製方式は 9 ページで、抽出内容も一致しなかった。Firefox の印刷はまだ確認していない。このほか、記事タイトルのアクセシビリティ、モード変更、印刷後の状態、画像読み込み、サイズ変更、先読み未完了・失敗・キャンセル、同時ナビゲーション、セッションの競合を検証する必要がある。

これらは前向きな試作結果だが、アプリ上の自動先読みはまだ実装されていない。先読みを始める操作・予測と、上記の互換性・資源管理を統合してから採否を決める。

### 印刷差の追加調査と先読み管理の部品化

印刷用の本文複製を、通常記事と同じ `main`、記事スクロール領域、記事、グリッドの構造に直した。さらに、iframe で読み込み済みのフォントに対応する親文書側のフォントを先に読み込む試作を加えた。Chromium の数式記事では、通常の PDF 出力で両方とも 10 ページ・抽出テキスト一致となり、1・3・9 ページを 96 dpi で画像化した比較も一致した。n 段での印刷後は試験した読書位置を維持し、1 段へ切り替えた後の印刷もページ数・抽出テキストが一致した。

Firefox の実際の PDF 出力は未検証だが、印刷メディアを模擬し `beforeprint` を発火してフォントを待った状態では、数式記事の全体画像が通常記事と一致した。Chromium でも、親のフォントを先に読み込まないと、印刷中に使われる数式フォントが間に合わず、ページ数が一致してもテキストや数式配置が異なった。フォント読み込み直後に印刷した場合や、後から展開した詳細内で新たに必要になったフォント、Firefox の実際の印刷処理は引き続き検証が必要。

`src/scripts/reading-preload.ts` に、設定と画面幅に基づく準備判定、同時に一件だけの候補、準備中の中止、画面サイズ・設定の変更時の破棄、準備完了後 15 秒での破棄を管理する部品を追加した。準備完了は iframe 内で n 段が実際に構築され、フォントと画像の読み込みが落ち着いた後、2 フレームを確認して判定する。読書画面と判定式を共有し、前回の明示設定を優先する。開発サーバーを使う `scripts/experiments/reading-preload.browser.test.mjs` では Chromium・Firefox とも、初回の自動判定、前回設定、中止、候補の取得、設定変更・画面サイズ変更・保持期限による破棄、一覧画像の一致を確認した。

この部品はまだ一覧や遷移に接続しておらず、自動先読みの完成ではない。採用するには、準備済み iframe の実際の操作・履歴・印刷を安全に接続し、未完了時の通常遷移やリソース管理を含めて検証する必要がある。

Chromium の追加試験では、iframe で使用済みの数式フォントだけを親でも読み込むようにし、親のフォント取得を 1.5 秒遅らせたうえで、記事を開いてすぐ PDF 出力した。7 件のフォント要求が発生し、出力処理には約 4.9 秒かかったが、通常記事と同じ 10 ページ・抽出テキスト一致だった。これは Playwright の PDF 出力での 1 回の試験であり、対話式の印刷ダイアログやすべてのネットワーク環境での保証ではない。

先読み管理部品の追加試験では、候補を別の記事へ切り替えたときの前候補の中止、存在しない記事、応答が遅い記事の期限切れ、破棄済み管理器の再利用防止も Chromium と Firefox で確認した。

### 2. ブロック単位の計測・描画準備と協調的な中止（削減幅を狙う試作）

1 の小規模な改善の後、全文を一括で組版しない方式の成立性を試す。iframe に限定せず、同じスタイルを適用した計測領域で段落・数式・リスト・表などを安全な単位に分け、少量ずつ配置・計測し、位置情報を蓄積する。区切りごとにブラウザーへ処理を返し、中止・候補変更を確認する。目標は総時間だけでなく、最大の連続処理時間、短いホバーで不要になったときの CPU、同時にレイアウトする DOM とピーク PSS を減らすこと。

まず数式記事の一部だけで、全文レイアウトとブロック計測の矩形・余白・段の画像が一致するか検証する。画像・フォント、隣接余白、リスト番号、詳細の開閉、長い表、一つの長い数式段落を含める。一致しない場合は差の原因と対応コストを先に判断し、正しさを確認せず全文・遷移へ拡張しない。

成立した場合だけ全文へ広げ、全体の長さ・位置情報と表示対象の段が確定した結果を遷移で実際に使う。先頭だけの未完成プレビューや推定の全長を、準備完了とは扱わない。組み直す際に再び全文レイアウトが必要なら、その費用を必ず計上し、過去の DOM 移送試作と同じ制約を解消できていなければ不採用とする。

JavaScript を小分けにしても一つの同期レイアウト中には中止を受け付けられない。巨大な単一ブロックが時間を支配する場合や、分割によって総 CPU・準備完了時間が増える場合も記録する。既存測定で小さかった `ReadingFragments.measure()` のループを分割するだけの実装は、主候補にしない。

### 3. 全文幾何と必要な表示の再利用（条件が整った場合の次候補）

1・2 の結果から、再計測・再構築がなお支配的で、再利用可能な単位が確認できた場合に検討する。キャッシュは記事内容・段幅・画面寸法・フォント・画像寸法・詳細の開閉などを条件とし、軽い位置情報と必要な表示だけを保持する。初回の準備と、同じ記事を再び候補にした場合の効果を分けて測る。

以前に追加効果が小さかった断片矩形だけの移送や、移送後に全文を再レイアウトする方式は繰り返さない。最初の候補では効かず再ホバーだけが速い場合、キャッシュの成功として記録しても、初回先読みの負荷を解決したとは扱わない。大きな DOM や文書を常駐させなければ効果が出ない場合は、軽量化の候補として見送る。

### 比較条件と各段階の判断

各試作では、候補・現在の作業ツリー・読書 iframe なし（通常の HTML 先読みは残す）を比較する。Chromium / Firefox、軽い記事 / 数式記事、同じ画面・保存設定・通信条件で実行し、0 / 300 / 1000 / 3000 ms の待ちと、開かずにポインターを外す場合を含める。

#### 実 PDF と印刷後の位置

`scripts/experiments/reading-no-iframe-print-position.mjs` を追加した。手順は次のとおり。

  どちらも `7997c3d` を同じ `astro preview` で配信して再現した（`pdf/before-astro/`、`pdf-diagnostic/`）。Python サーバーで配信した場合と、新しいコンテキストの場合は起きなかった。原因は特定していない。

計測器は新しいファイル `reading-no-iframe-pinned-comparison.mjs` で、既存の比較スクリプトは変更していない。区間の境界は次のとおり。

| S1 | マウス押下を送る直前 |
| S2 | 表示可能イベント（記事準備後の 2 rAF）を観測した時点 |

クリック前は S0..S1、クリック後は S1..S3 とした。指標の定義は次のとおり。

- CPU はブラウザーのプロセス木の utime+stime に、木の中のプロセスの cutime+cstime を加えた。木の中で回収された子プロセスの CPU も含む。消えた PID は数えており、48 試行で 0 だった。
- PSS は smaps_rollup の合計を 100 ms 間隔で取った概算で、間隔の間のピークは取り逃し得る。
- サンプル 1 回の所要時間は中央値 24.8 ms、最大 37.9 ms。計測ワーカーの CPU は 1 試行あたり中央値 60.5 ticks で、変更前後に同じだけかかる。
- 操作の往復時間は人間の入力遅延ではなく、rAF の時刻は厳密な画素表示時刻ではない。

外乱は試行ごとに記録した。固定 CPU の使用量から自分のプロセス群の分を引いた値、システム全体の使用率、ロードアベレージ、固定 CPU の周波数である。注記の基準は測定前に `reading-no-iframe-pinned-summary.mjs` に固定した。外部の使用量が固定 CPU の容量の 5% を超える試行を含むペア、またはペア内のシステム使用率の差が 15 ポイントを超えるペアに注記する。結果は 0 ペアで、外部の使用量は中央値 0.6%、最大 1.8%、システム使用率は 5.4〜9.7%、load1 は 2.4〜3.5 だった。L3 キャッシュ、メモリー帯域、ターボの電力枠は他のジョブと共有したままで、固定では隔離できない。周波数（S0 の固定 CPU 平均）は 1.27〜1.82 GHz の範囲で変動した。ブラウザーは各エンジンで再利用し、OS のページキャッシュとサーバーは温まっている。各試行の新しいコンテキストは HTTP キャッシュと storage が空だが、コールドとは呼ばない。48 件にエラーはなかった。

条件別（`docs/reading-no-iframe-summary-pinned-20261105.json`）では、変更前に準備済み iframe を使えたのは Chromium の tips-python・1000 ms の 3 回だけだった。その条件でクリックから表示可能までは 39→226 ms に延びた。数式記事の 1000 ms では、この環境で準備が 1 秒以内に終わらず、一度も使えなかった。それでも、クリック前の CPU は Chromium で 114→8 ticks、Firefox で 163→37 ticks、PSS ピーク増分は 168.5→3.5 MiB、88.1→31.4 MiB と大きく減った。一方、表示可能までは Chromium で 735→1004 ms、Firefox で 725→828 ms に延びた。Firefox は 12 試行とも準備済みを使っていないが、それでも 11/12 ペアで遅くなった。iframe の準備が HTML 以外の資源（フォントなど）も先に取得し、温めていた効果と考えられる。ただし原因は分解して測っていない。

指標の外乱への強さは次のとおり。

- PSS は CPU の取り合いの影響をほとんど受けないので、主な根拠にする。クリック前の削減と、クリック後のクリック時比の増加は、どちらも 23〜24/24 ペアで向きがそろう。
- CPU ticks はキャッシュの取り合いで多少増え得るが、クリック前の削減は 24/24 ペアでそろう。クリック後の CPU は向きがそろわず、差は判断できない。
- 表示までの時間は外乱込みの実時間として扱う。外部負荷が小さい試行でも、23/24 ペアで変更後が遅かった。

各条件 3 回しかないので、p 値は主張の根拠にしない。

#### main へのマージ判断

**マージ可能と判断する。** 作業ツリーの差分（製品コード 2 ファイル、試験 1 ファイル、実験スクリプト 5 ファイル、記録）をレビューしてコミットすることが前提である。根拠は次のとおり。

- 一覧のホバーやフォーカスで iframe を作らないという維持仕様を、両エンジン・両モードで満たした。
- 通常遷移の回帰（遷移中の操作、履歴と読書位置、リンク、設定の未設定・不正値・取得不可、切替と保存、ちらつき、一覧、退避と遅延初期化、HTML 先読み）を両エンジンで確認した。全ブラウザー試験は 88/88 成功。
- 実 PDF と印刷後の位置を両エンジンで確認した。その過程で見つかった既存の印刷後の位置ずれも直した。
- 性能では、クリック前の CPU と PSS が両エンジンで一貫して減り、表示を高速化できた場面は Chromium の軽い記事を長くホバーした場合に限られた。この表示時間の延長（中央値 +52〜156 ms、最大の条件で +274 ms）は、投機的な事前処理をやめた代償として受け入れる。前節の最終判断（iframe 先読み方式は不採用）とも整合する。

残る制約:

- 今回の性能値は単一環境・各条件 3 回の結果で、環境により大きく変わり得る（元マシンの Firefox の値を参照）。
- 表示までの時間の延長は、iframe 準備による資源の事前取得がなくなった影響と考えられるが、分解して測っていない。
- `reading-motion` の段送りアニメーション試験は負荷下で不安定だった。途中のフレーム数ではなく「途中の位置を通ること」と「到着まで 150 ms 以上かかること」で判定するよう直し、全 CPU に負荷をかけた状態でも 5/5 回成功した。
- `astro preview` 配信時に Chromium の印刷で起きる 2 つの差（数式フォントの代替、同じ URL へ戻った直後の 1 ページ化）は既存の現象で、原因は未特定。本番配信（GitHub Pages）の挙動はこの環境では確認していない。
- 実 PDF は headless の自動化経由（`page.pdf()`、Marionette）で、対話式の印刷ダイアログは確認していない。
- `scripts/experiments/` の旧 iframe 試験（`reading-preload*.browser.test.mjs` 等、冒頭のタグに保存）は削除済みモジュールを前提にした過去の記録で、現在のコードでは動かない。
