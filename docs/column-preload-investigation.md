## 採らなかった方式：画面外の iframe でn段を先読みする（2026-11-05）

一覧の記事リンクにホバーしたとき、画面外の iframe で記事をn段まで組み立てておき、クリックしたらその画面を使う方式を試した。準備済みの画面を使えたときは速かったが、次の3点を解消できず、採らなかった。iframe の先読みは削除した。

- 数式記事では、本文全体のレイアウトに伴うCPUとメモリの負荷が大きい。
- ホバーしても記事を開かなかった場合に、その負荷が無駄になる。
- Firefoxでは、ホバーからクリックまでの代表的な待ち時間（300 ms、1 s）の間に準備が終わらず、準備済みの画面を使えなかった。

このときに、段組みを選んでいない閲覧者には画面幅によらず1段で表示するようにした。

計測の手順と値、試した派生案（矩形の計測値の移送、画面外の段の生成の省略、早期中止など）の記録は、コミット `3d10de7` の版のこの文書の前半にある。計測スクリプト、実験パッチ、生データはタグ `reading-preload-investigation-20261105` にある。

```sh

git show reading-preload-investigation-20261105:scripts/experiments/reading-candidate-benchmark.mjs
```

## 表示までの内訳と数式フォントの先読み（2026-11-06）

iframe 先読みをやめて延びたクリックから表示までの時間を、重い事前処理を戻さずに取り戻すための計測と対策。計測は `scripts/measure-article-open.mjs`（本番ビルドを `astro preview` で配信、1440×900、ホバー 300 ms 後にクリック、各条件 3 回）。cold は新しいコンテキストで一覧から最初に開く条件、warm は同種の記事（数式記事なら tips-julia）を先に開いた条件。値は中央値（ms）で、単一環境・少数試行の結果である。

### 内訳（対策前）

| 記事・段組み | Chromium cold / warm | Firefox cold / warm |
| --- | --- | --- |
| tips-python・1段 | 122 / 97 | 167 / 158 |
| tips-python・n段 | 138 / 129 | 230 / 187 |
| symmetric-polynomial・1段 | 429 / 326 | 448 / 269 |
| symmetric-polynomial・n段 | 692 / 605 | 740 / 606 |

- 数式記事では、cold と warm の差（90〜180 ms）の大半が MathJax フォントだった。cold ではフォントがレイアウト中に順に見つかって読み込まれ、届くたびにレイアウトし直す（Chromium の 1 段で、差し替えから読み込み完了までのレイアウトが cold 237 ms、warm 105 ms）。
- n段では、差し替え直後に本文が 1 段の幅（768 px）でレイアウトされてから、リーダーが段の幅（608 px）でやり直す。Chromium の数式記事で最初のレイアウトは 115〜169 ms。
- n段の組み立て（読み込み完了から表示まで）は数式記事で約 300 ms。Chromium ではスタイル計算約 150 ms とレイアウト約 100 ms で、段に複製した約 1 万 3 千ノードの分である。

### 対策：ホバー時に記事の数式フォントを読み込む

ビルド時に、記事の CHTML のスタイルシートと本文から、実際に読み込まれるフォントを求める（`lib/math-fonts.ts`）。`@font-face` のうち、本文に現れる class・要素の規則が参照するものだけを選ぶ。symmetric-polynomial・tips-julia・how-to-write の 3 記事で、Chromium / Firefox × 1 段 / n 段のすべてで、ブラウザーが実際に読み込むフォントと一致した。一覧の記事リンクがこの一覧を持ち、Astro の HTML 先読みと同じ条件（80 ms のホバーまたはフォーカス、離れたら中止、オフライン・低速回線では行わない）で読み込む（`src/scripts/math-font-prefetch.ts`）。

`<link rel="prefetch">` で HTTP キャッシュに入れるだけでは、ほとんど効果がなかった（Chromium の数式記事・1 段 cold 429→427 ms）。フォントは差し替え後にやはり順に見つかって届き、そのたびにレイアウトし直すためである。Astro の差し替えは同じ文書の中で行われるので、`FontFace.load()` で文書のメモリに読み込んでおくと、記事の `@font-face` が同じ URL を指したときにすぐ使われる。読み込んだフォントは独自の名前で、`document.fonts` には加えないので、一覧の表示は変わらない。

| 数式記事（cold） | 対策前 | link prefetch | FontFace |
| --- | --- | --- | --- |
| Chromium・1段 | 429 | 427 | 304 |
| Chromium・n段 | 692 | 656 | 592 |
| Firefox・1段 | 448 | 378 | 340 |
| Firefox・n段 | 740 | 727 | 649 |

4 条件とも同じ向きに 90〜125 ms 短くなり、warm とほぼ同じ水準になった。数式のない記事はフォントがないので変わらない。ホバーで読み込むのは記事が使うフォントだけで、symmetric-polynomial で 7 本、約 181 KiB（うち mjx-tex-n が 161 KiB）。

### 試して採用しなかった案：n段で 1 段の幅のレイアウトを省く

n段が保存されているときに、表示準備中の本文を 1 段の幅でレイアウトしない案を試した。head のスクリプトが差し替え前の新しい文書に `rm-pending-multi` を付け、その間は `.rm-source` を `display: none` にする。リーダーは最初のフレームでこの class を外してから n段を適用するので、本文は段の幅で 1 回だけレイアウトされる。

最初の計測では数式記事のn段が 100〜180 ms 速く見えたが、これは費用を表示の後へ移しただけだった。本文をレイアウトしないと、数式フォントはリーダーのレイアウトで初めて見つかって読み込まれる。フォントは記事を見せた後に届き、表示の約 300 ms 後に記事が測り直された。印刷後の位置と履歴からの位置復元の試験も、この測り直しで失敗した。

表示後の測り直しをなくすため、記事が使う数式フォントをすべて head で preload し、リーダーの最初のフレームでフォントの読み込み中なら最大 1 s 待ってから測って表示するようにした。これで Chromium・Firefox とも表示後の測り直しは消え、ブラウザー試験もすべて通った。待ちを外すと、Firefox では preload があっても表示後に測り直す。

数式記事で、ホバー時のフォント読み込みだけの現状、現状に全フォントの preload だけを加えたもの、この案の 3 つを交互に 6 回ずつ計測した中央値（ms）。計測中は他の重い処理が動いていた（load average 7〜20）ため、絶対値は上の表と比べられない。

| 数式記事・n段 | 現状 | 現状＋全フォント preload | この案 |
| --- | --- | --- | --- |
| Chromium cold | 562 | 573 | 515 |
| Chromium warm | 547 | 543 | 503 |
| Firefox cold | 660 | 704 | 885 |
| Firefox warm | 604 | 594 | 519 |

Chromium は約 45 ms、Firefox の warm は約 85 ms 短くなったが、Firefox の cold は 225 ms 長くなった（6 回とも 859〜942 ms）。Firefox の cold では、リーダーの最初のフレームの時点でまだフォントが届いておらず、その待ちがそのまま表示を遅らせる。全フォントの preload だけでははっきりした効果がなく、1 段ではどの案も差がなかった。Firefox の初回を大きく遅らせるため採用しなかった。

再び試すなら、まず Firefox でフォントが遅れる理由を調べる必要がある。その一因だった、ホバー時に読み込んだフォントを Firefox が使い回さない問題は、次の節で直した。

全フォントのpreloadは、後に別の理由で採用した（PR #24、末尾の「記事を直接開いたときの数式フォントの到着」）。ここでの比較は一覧からのクリックから表示までの時間で、差が出なかった。PR #24 では直接の読み込みのTBTを比べ、フォントの到着による再レイアウトが減ったことを確かめた。

### Firefox でのフォントの使い回し

差し替え後に記事が要求したフォントを Resource Timing で見ると、Chromium ではホバー時に読み込んだ 7 本のどれも要求し直さなかったが、Firefox は 7 本すべてを要求し直していた。HTTP キャッシュから来るので転送量は 0 だが、レイアウト中に順に見つかって届くので、`FontFace.load()` で先に読み込んだ意味がなかった。

Firefox は、文書のフォントセット（`document.fonts`）にあり、記事の `@font-face` と同じ名前を持つフォントだけを使い回す。独自の名前のまま `document.fonts` に加えても使い回さなかった。そこで、ビルド時の一覧に `@font-face` の名前も入れ（`data-math-fonts` は `[名前, URL]` の組の JSON 配列）、ホバー時にその名前でフォントを作って読み込み、`astro:after-swap` で `document.fonts` に加える。MathJax の `@font-face` は名前と URL だけを持つので、どちらのフォントが選ばれても表示は同じである。ホバー時に加える版も試したが、表示までの時間は同じだったので、一覧のフォントセットを変えない差し替え時の版にした。

数式記事でホバー 300 ms 後にクリックし、変更前と変更後を交互に 6 回ずつ計測した中央値（ms、クリック→表示）。2 回の計測の値を並べる。

| 数式記事・cold | 変更前 | 変更後 |
| --- | --- | --- |
| Firefox・1段 | 508 / 463 | 374 / 396 |
| Firefox・n段 | 788 / 776 | 616 / 650 |

Firefox の初回は 70〜170 ms 短くなった。warm は変わらない。Chromium では 1 段の初回を 12 回ずつ交互に計測し、中央値は変更前と変更後で同じ（343.5 ms）だった。`tests/math-font-prefetch.browser.test.mjs` は、差し替え後に要求し直すフォントが記事の `<link rel="preload">` のものと 1 KB の MJX-TEX-ZERO だけであることを確かめる。独自の名前に戻すと Firefox で失敗する。

### 残る課題

> 2026-11-06 時点の記述。1 段の幅での最初のレイアウトは、その後の「n段の本文を差し替え前に段へ入れておく」（一覧からの遷移）と「直接の読み込みでも先に段へ入れておく」でなくなった。段の組み立ての費用は残っている（冒頭の「残っている課題」）。

n段の 2 つの費用は残っている。1 段の幅での最初のレイアウトは、上の案を採用しなかったのでそのまま残る。段の組み立て（読み込み完了から表示まで約 300 ms、段に複製した約 1 万 3 千ノードのスタイル計算とレイアウト）は、減らすには段の組み立て方そのものを変える必要がある。

## n段の組み立ての内訳と短縮（2026-11-06）

### 内訳

読み込み完了から表示までの間に、リーダーの処理へ `performance.mark` を一時的に入れて区切り、Chromium ではトレースで区間ごとのスタイル計算とレイアウトの時間を見た（数式記事、n段、1440×900）。初回フレームの中で本文全体（約 9 千要素）のスタイル計算とレイアウトが繰り返されていた。

- `.rm-plane` と `:root` に JS で設定するカスタムプロパティ（`--rm-w`、`--rm-l`、`--rm-header-height` など）は継承されるため、値が変わると下にある本文と複製のすべての要素でスタイルを計算し直す。表示済みの数式記事で `.rm-plane` の継承されるプロパティを 1 つ変えるだけで、Chromium 約 120 ms、Firefox 約 100 ms かかった。登録済みの継承しないプロパティでは 0 ms だった。
- 元の本文は、`rm-active` を付けた直後のページの寸法の読み取りで一度レイアウトされ、段の幅を設定して測るときにもう一度、段に移したあとにさらにもう一度レイアウトされていた。
- 画面に入らない先の列（1440 px 幅では 4 列目）も、表示前に複製してスタイル計算とレイアウトをしていた。

### 変更

1. リーダーが設定するカスタムプロパティを `@property` で継承しないものとして登録し、使う要素（`.rm-track`、`.rm-slot`、`.rm-content`、`.rm-shade`）だけが親から `inherit` で受け取るようにした。`--rm-header-height` は `:root` ではなく `.rm-article` に設定する。
2. n段にするときは、ページの寸法を読む間は元の本文を文書から外しておき、段の幅と `--rm-w`・`--rm-h` を決めてから段に入れて測る。元の本文のレイアウトは段の幅で 1 回になる。外した位置で測るための CSS（`.rm-active .rm-source:not(.rm-content)`）は不要になったので削除した。
3. 画面の外にある列は、1 フレーム後に複製を入れる。画面に入る列は従来どおりその場で入れる。

`tests/reading-assembly.browser.test.mjs` で、本文の要素にリーダーの変数が届いていないこと、表示時に画面内の列がそろっていて画面外の列が後から埋まることを確かめる。変更 1 と変更 3 をそれぞれ戻すと、この試験は両エンジンで失敗する。

### 結果

本番ビルドで変更前と変更後を交互に 8 回ずつ、n段で計測した中央値（ms）。計測中は他の処理が動いていた（load average 7〜14）。

| n段 | クリック→表示 変更前 | 変更後 | 読み込み完了→次のフレーム 変更前 | 変更後 |
| --- | --- | --- | --- | --- |
| Chromium・数式・cold | 583 | 473 | 396 | 235 |
| Chromium・数式・warm | 476 | 337 | 391 | 246 |
| Firefox・数式・cold | 759 | 658 | 424 | 308 |
| Firefox・数式・warm | 568 | 458 | 408 | 284 |
| Chromium・tips-python・cold | 149 | 119 | 77 | 51 |
| Firefox・tips-python・cold | 221 | 198 | 111 | 83 |

数式記事では、表示まで両エンジンで約 100〜140 ms 短くなった。内訳では、変更 1 と 2 で約 90〜130 ms、変更 3 で約 30 ms 短くなり、8 条件すべてで同じ向きだった。変更後も残る費用は、段の幅での本文のレイアウト 1 回（Chromium 約 80 ms、Firefox 約 110 ms）と、画面内の列の複製のスタイル計算・レイアウト・描画である。

## n段の本文を差し替え前に段へ入れておく（2026-11-06）

一覧からn段の記事を開くと、本文は差し替え直後に 1 段の場所で 1 段の幅（1440×900 で 768 px）でレイアウトされ、リーダーの最初のフレームで段に移されて段の幅（608 px）でもう一度レイアウトされていた。上の「試して採用しなかった案」は最初のレイアウトを遅らせたため、数式フォントの発見も遅れて Firefox の初回が遅くなった。今回はレイアウトの時期を変えず、最初のレイアウトを段の幅と段の中で行う。

### 変更

1. `Layout.astro` の head のスクリプトで、`astro:before-swap` のときに n段が保存されていれば、まだ描画されていない新しい文書の `.rm-source` を `.rm-plane > .rm-track > .rm-slot` に入れる（リーダーの `mountSlot()` と同じ構造で、`.rm-shade` と `.rm-paper` も付ける）。本文の幅は `var(--rm-column-width)` にし、`.rm-reader` の `hidden` を外し、`html` に `rm-premount` を付ける。一覧での遷移だけが対象で、直接のアクセスと再読み込みは従来どおり。
2. 段の本文に効く CSS（`padding-inline` と h1 の `margin-top`）を `.rm-active` から切り離して `.rm-plane .rm-content` にした。記事の外枠の n段用の規則（`.rm-article` の `position: fixed`、`.rm-layout`、`.rm-article-scrollport` の `overflow`、サイドバーを隠す規則）は `:is(.rm-active, .rm-premount)` にした。ヘッダーの規則は `.rm-active` のままなので、表示準備中に見えているヘッダーは変わらない。記事は従来どおり `rm-pending` で隠れている。
3. リーダーは、本文がすでに段にあればその段を最初の段として使い、外して入れ直さない。幅は同じ値を px で設定し直すだけである。1 段で始める場合（印刷中、別のタブで設定が変わった場合、fallback の後）は本文を元の場所に戻す。元の場所は `.rm-reader` の直前である。
4. 10 秒の fallback は、本文を元の場所に戻して `rm-premount` を外してから記事を見せる。

段の幅の計算はリーダー（ルーラーの幅と表示領域の幅の小さいほう、1/1024 px に丸める）と CSS（`min(38em, 100vw - 2rem)`）で異なる。1440×900 ではどちらも 608 px になる。狭い画面や拡大表示で値が違うときは、リーダーが幅を設定し直したときにもう一度レイアウトされるだけで、従来と同じになる。

最初の版では本文を段に入れて幅をそろえるだけで、記事の外枠には `rm-premount` を付けなかった。Chromium ではリーダーの最初のフレームの本文のレイアウトが消えたが、Firefox では約 110 ms のうち 30 ms ほどしか減らなかった。リーダーが `rm-active` を付けると `.rm-article` が `position: fixed` になり、Firefox はその下の箱を作り直して本文をレイアウトし直す。外枠の規則も差し替えの時点で当てるようにして、Firefox でも消えた。

### 確認

## 差し替え直後の 2 回目のレイアウト：数式フォントの二重定義（2026-11-06）

上の節で調べずに残した、差し替え直後の 2 回目の本文全体のレイアウトの原因を調べて取り除いた。

### 原因

記事のインラインの MathJax CSS には MJX-TEX-* の `@font-face` がある。一覧はホバー時に同じ名前・同じ URL の `FontFace` を読み込み、差し替え時に `document.fonts` に加える（「Firefox でのフォントの使い回し」）。そのため差し替え後の文書には、同じ名前のフォントが 2 つずつある。読み込み済みのホバー時のフォントと、まだ読み込んでいない記事の `@font-face` のフォントである。

MathJax のフォント指定はどれも `font-family: MJX-TEX-ZERO, MJX-TEX-N` のように MJX-TEX-ZERO から始まる。MJX-TEX-ZERO は 1 KB でグリフをほとんど持たない。最初のレイアウトでは、読み込み済みの ZERO にない文字について、同じ名前の未読み込みの ZERO（記事の `@font-face`）も候補になる。ブラウザーはそれを読み込み始め、届いた時点でフォントが変わったとして本文全体をレイアウトし直す。

Chromium のトレースでは、差し替えの約 110〜140 ms 後に `mjx-tex-zero` の `RemoteFontLoaded` があり、その直後に本文全体（約 1 万 2 千 5 百オブジェクト）のレイアウト約 47 ms と、フォントによるスタイル計算約 15 ms があった。その間のレイアウトの無効化は約 1 万 2 千件で、理由はすべて "Fonts changed" だった。Firefox の cold でも、差し替えの約 125 ms 後に `mjx-tex-zero.woff2` を要求し、届いた直後に 40〜47 ms の Reflow があった。Firefox の warm では、先に直接開いた別の数式記事で ZERO を読み込んだ状態なので、要求も Reflow もなかった。

### 試して効かなかった案

- MathJax のフォント指定から MJX-TEX-ZERO を外す：同じことが MJX-TEX-N で起きた。
- ホバー時のフォントを `document.fonts` に加えない：記事の `@font-face` のフォントはやはり最初のレイアウトの後に読み込まれ、Firefox での使い回しもなくなる。
- 差し替え時に記事の `@font-face` のフォントに `.load()` を呼ぶ：最初のレイアウトには間に合わない。
- ZERO の読み込みを遅らせる：レイアウトし直しの時期が後ろにずれるだけだった。

記事の `@font-face` のうち、ホバー時に読み込んだ名前の規則を最初のスタイル計算の前に消すと、Chromium で差し替え後の本文全体のレイアウトが 1 回になり、Firefox でも Reflow が増えなかった。

### 変更

1. ビルド時（`[slug].astro`）に、一覧の `data-math-fonts` と同じ一覧（`mathFontFaces`）にあるフォントの `@font-face` を CSS から取り出し、1 規則ずつ `<style data-math-font="名前" data-math-font-url="URL">` に入れる（`lib/math-fonts.ts` の `separateMathFontFaces`）。名前と URL の両方が一覧と一致する規則だけを取り出し、残りの CSS は元のまま `<style>` に入れる。`<link rel="preload">` には `data-math-font-preload` を付けた。
2. `math-font-prefetch.ts` は `astro:before-swap` で、ホバー時のフォントを `document.fonts` に加え、まだ描画されていない新しい文書から、状態が `loaded` のフォントと名前・URL が一致する `<style data-math-font>` と、URL が一致する preload を消す。読み込み中・失敗・未ホバーのフォントの規則は残るので、直接のアクセス、タッチ、ホバーなしのクリック、遅い回線では従来どおりになる。
3. フォントを加える時期を `astro:after-swap` から `astro:before-swap` にした。Astro は差し替えと `astro:after-swap` の間でスクロール位置を戻し、履歴の移動ではそこでレイアウトが起きる。そのときに記事の規則がなく、ホバー時のフォントもまだ加わっていないと、代わりのフォントでレイアウトしてしまう。

MathJax の `@font-face` は名前と URL だけを持つので、ホバー時のフォントは消した規則と同じフォントになる。Firefox での使い回しも同じ前提に立っている。

印刷は、Chromium（`page.pdf()`）と Firefox（WebDriver BiDi の `browsingContext.print`）で、ホバーしてから開いた数式記事を PDF にし、埋め込まれたフォントが変更前と同じ（mjx-tex-n、-so、-lo、-s3、-s4 など）であることを `pdffonts` で確かめた。`document.fonts` に加えたフォントは印刷でも使われる。

### 確認

`tests/math-font-prefetch.browser.test.mjs` に 2 つの試験を加えた。1 つ目は、ホバーして読み込みが終わってから数式記事を開き（n段・1段）、クリック後に数式フォントの要求（Resource Timing）と `loadingdone` がないこと、各フォント名の `FontFace` が 1 つずつで `loaded` であること、∑ が MJX-TEX-N の幅で描かれることを確かめる。変更前のビルドでは両エンジンで失敗する（mjx-tex-n と mjx-tex-zero を要求し、各名前の未読み込みのフォントが残る）。2 つ目は、フォントの応答を 1.5 秒遅らせてホバー直後に開くと記事の規則が残ること、一覧へ戻って進むと規則と preload が消えること、別の数式記事（tips-julia）では読み込み済みでない名前の規則だけが残ることを確かめる。既存の試験の「差し替え後に要求し直してよいのは preload のファイルと MJX-TEX-ZERO だけ」は「何も要求しない」に改めた。

Chromium のトレース（各条件 3 回）で、差し替え後の本文全体のレイアウトは変更前が 2 回（2 回目 47〜50 ms）、変更後が 1 回で、`mjx-tex-zero` の `RemoteFontLoaded` もなくなった。n段・1段、cold・warm の 4 条件で同じだった。Firefox の Gecko プロファイル（cold、n段・1段）では、`mjx-tex-zero.woff2` と `mjx-tex-n.woff2` の要求と、その直後の 40〜47 ms の Reflow がなくなった。差し替えの約 220〜240 ms 後の 45〜55 ms の Reflow は変更前からあり、今回の変更とは関係しない。

### 結果

本番ビルドを `astro preview` で 2 つ配信し、変更前（`feat/premount-column`）と変更後を交互に 12 回ずつ計測した中央値（ms、`TRACE=0`）。計測中は他の処理が動いていた（load average 15〜36、中央値 17）。

## n段の本文を直接の読み込みでも先に段へ入れておく（2026-11-06〜08）

「n段の本文を差し替え前に段へ入れておく」の変更は一覧からの遷移だけが対象だった。アドレスバーからの読み込みと再読み込みには差し替えがないので、本文はパース中に 1 段の幅（768 px）でレイアウトされ、リーダーの最初のフレームで段の幅（608 px）でもう一度レイアウトされていた。

### 試した案 1：リーダーの直後のスクリプト

最初に、`.rm-source` の直後にある `.rm-reader` のさらに後ろにパーサーを止めるインラインスクリプトを置き、head のスクリプトと同じ処理を `document` に行う案を試した。数式記事の HTML は 444 KB で、その大半が本文なので、パースの途中でブラウザーがフレームを描く。`.rm-source` が現れた時点で ResizeObserver を付けて調べると、Firefox では 3 回とも、本文全体（約 9 千要素）を 768 px で描いてからスクリプトが動いた。Chromium も 3 回のうち 1 回は、本文の約 9 割がそろった時点で 768 px で描いた。こうなるとレイアウトは従来どおり 2 回で、得がない。

### 試した案 2（A）：`.rm-source` の先頭のスクリプト

次に、`.rm-reader` を `.rm-source` の直前に移し、`.rm-source` の最初の子にインラインスクリプトを置いた。スクリプトは自分を取り除き、パース中なら head のスクリプトの `premountColumn()` を呼ぶ。HTML のパーサーは開いている要素そのものに子を追加していくので、段に移した `.rm-source` には残りの本文が段の中で追加される。本文を含むフレームはすべて段の幅になり、n段の表示は速くなった。

ただし Firefox では、1 段でも遅くなった。Gecko のプロファイラーで直接の読み込みを見ると、A だけにパースの途中で 55〜65 ms の Styles（スタイル計算）が 1〜2 回入る。数式記事で 4 回ずつ測ると、読み込み完了までの Styles は main と次の B で 1〜6 ms、A で 57〜120 ms（1 段）と 61〜65 ms（n段）だった。本文の途中で実行されるパーサーを止めるスクリプトが、Firefox にスタイル計算をさせていると考えられる。理由までは調べていない。

### 変更（B）：MutationObserver で段へ移す

1. `ReadingMode.astro` が `.rm-source` を slot として受け取り、`.rm-reader` の直後に置く（`[slug].astro`）。ルーラーとリーダーのモジュールスクリプトは本文の後ろに置く。A の途中の版でモジュールスクリプトを `.rm-reader` の前に置いたところ、Firefox で一覧から数式記事を開くとき、差し替えから `astro:page-load` までが 60〜90 ms 長くなった。後ろに戻すと変更前と同じになった。理由は調べていない。
2. head のスクリプトは、n段の保存、記事ページ、印刷でないこと（`wantsColumn()`）を満たす通常の読み込みのときだけ、`document` に MutationObserver（childList、subtree）を付ける。`.rm-source` が文書に入ったら監視をやめて `premountColumn(document)` を呼ぶ。遅くとも `DOMContentLoaded` で監視をやめる。1 段ではパース中に何も動かない。
3. MutationObserver のコールバックは、`.rm-source` を挿入したパーサーのタスクが終わったあとのマイクロタスクで動く。それまでにパーサーは本文の一部を `.rm-source` に入れている。数式記事（`.rm-source` の下に 8984 要素）では、移した時点で Chromium が 1089〜3735 要素、Firefox が 2445〜4973 要素だった。HTML を `.rm-source` の直前で 400 ms 止めると、Firefox では 5281〜8984 要素になった。それでも、移す前にフレームが描かれたことはなかった。両エンジンで、止める位置なし、`.rm-source` の直前、開始タグの直後、全体の半分の 4 通りを 4 回ずつ試し、本文を含むフレームが 608 px 以外で描かれたことは一度もなかった。
4. 段に入れる前の本文の場所は `.rm-reader` の直後になった。リーダー（1 段で始める場合）と 10 秒の fallback は本文をそこへ戻す。グリッドの配置は CSS で指定しているので、1 段の見た目は変わらない。

移す時点ですでに入っている本文の費用も見た。Chromium のトレースでは、A と B の Layout イベントは同じだった。どちらもパース中に段の中で本文全体のレイアウトが 2 回あり（13011 オブジェクト、62〜115 ms と 47〜60 ms）、読み込み完了から表示までは複製の 3029 オブジェクトだけだった。main では、この区間に本文全体（12852 オブジェクト、48〜98 ms）のレイアウトがもう 1 回ある。Firefox のプロファイルでも、B の読み込み完了までの Reflow は 196〜229 ms で、main の 194〜226 ms と同じ程度だった。移す前にできたボックスを作り直す費用は、どちらのエンジンでも見えなかった。

数式記事のn段は、A も B も 4 条件で 80〜120 ms 短くなった。読み込み完了から表示までは、main の 183〜230 ms から A・B とも 100〜145 ms になった。同じ回で B と A を比べると、Firefox では 8 条件すべてで B が速く（差の中央値 −5〜−25 ms、7〜10/12 回）、1 段の数式記事・warm で −25 ms、tips-python・1 段・cold で −11 ms だった。Chromium では B と A の差は −23〜+11 ms で、向きは一定しなかった。数式のない記事と Chromium の 1 段の差は、この負荷では計測の揺れの範囲である。

一覧からの遷移（クリック→表示）では、main、A、B に一定の向きの差はなかった。数式記事のn段は Chromium で 349 / 328 / 321 ms（cold）と 309 / 295 / 288 ms（warm）、Firefox で 384 / 383 / 393 ms と 372 / 385 / 373 ms（main / A / B）だった。

### 判断

B を採用する。n段の短縮は A と同じかそれ以上で、1 段ではパース中に何も実行しないので、A が Firefox で払っていたスタイル計算がない。B では、移す時点で本文の一部がすでに `.rm-source` に入っている。この費用は Chromium のトレースにも Firefox のプロファイルにも現れなかった。ただし、パーサーのタスクの区切りはブラウザーと回線の速さで変わるので、試験はフレームごとの幅で確かめている。

## 記事を開くときの文書全体のスタイル計算（2026-11-08）

記事を開くあいだに、`<html>` のクラスは何度か変わる（`rm-pending`、`rm-premount`、`rm-active`、`rm-ready`）。Chromium のトレースでは、そのたびに文書全体（約 1 万 1 千要素）のスタイル計算が 35〜55 ms かかっていた。Firefox でも `rm-pending` を外すときに本文全体のスタイルを計算し直していた。

### 原因

1. `@tailwindcss/typography` は `.prose :where(p):not(:where([class~=not-prose],[class~=not-prose] *))` のように、`not-prose` の中を除く条件を `class` 属性のセレクターと全称の子孫で書く。Chromium はこの形があると、どの要素の `class` が変わっても、その下の全要素のスタイルを計算し直す。`<html>` のクラスが変わると文書全体になる。調査時のトレースでは `rm-ready`、ビュー遷移の終わり、`rm-pending` を外すときの 3 回が 35〜55 ms だった。プラグインにこの書き方を変える設定はない。
2. `reading-mode.css` の `.rm-active [data-site-header] > :not(.rm-toolbar)` は、右端の複合セレクターにクラス、ID、タグがない。Chromium は `<html>` に `rm-active` が付くと全要素を調べ直す。`rm-active` はn段のときだけ付く。
3. `html.rm-pending .rm-article-scrollport { visibility: hidden; }` の `visibility` は継承されるので、`rm-pending` を外すと本文の全要素のスタイルが変わる。Chromium と Firefox の両方で起きる。`opacity: 0` も試したが、Firefox では直らなかった。

### 変更

1. `astro.config.mjs` に Vite のプラグインを加え、Tailwind が CSS を生成した直後（どちらも `enforce: 'pre'`）に `[class~=not-prose]` と引用符付きの `[class~="not-prose"]` を `.not-prose` に書き換える。`:where()` の中なので詳細度は 0 のままで、一致する要素も変わらない。開発サーバーとビルドの両方に効く。ビルドした `dist/_astro/*.css` に `[class~=not-prose]` は残っていない（`.not-prose` が 172 か所、残る `class~=` は `[class~=lead]` だけで、これは右端にあるので対象の要素だけが調べ直される）。
2. 見出しの規則から `.rm-active` を外し、`[data-site-header] > :not(.rm-toolbar) { flex: 1; min-width: 0; }` にした。ヘッダーが flex になるのは `.rm-active` のときだけなので、ほかの場面では効かない。一覧、1 段とn段の数式記事、n段の tips-python を 390 px と 1440 px の両エンジンで main と比べ、ヘッダーとその子孫の位置と大きさはすべて同じで、ヘッダーのスクリーンショットも 1 バイトも違わなかった。違うのは計算値の `flex-grow` だけである。
3. 待機中の本文を `clip-path: inset(50%)` で隠す。`clip-path` は継承されないので、外しても子孫のスタイルは変わらない。n段の `position: fixed` の本文も切り取られ、ヒットテストからも外れる。
4. `visibility: hidden` は本文をアクセシビリティツリーからも外していたが、`clip-path` は外さない。そこで待機中は `.rm-article-scrollport` に `aria-hidden="true"` を付ける（`inert` は使わない）。
   - 一覧からの遷移では、head のスクリプトが `astro:before-swap` で `rm-pending` を付けるときに、新しい文書のスクロールポートにも付ける。
   - 直接の読み込みでは、head のスクリプトが動く時点でスクロールポートはまだない。PR #6 の MutationObserver をすべての記事の読み込みで付けるようにし、パーサーがスクロールポートを文書に入れたらその場で付ける。n段では従来どおり `.rm-source` も段へ移す。どちらも本文より前にあるので、監視はすぐ終わる。本文の中にインラインスクリプトは置かない（パーサーを止めるスクリプトで Firefox にスタイル計算が入ったため）。
   - 外すのは `rm-pending` を外す 2 か所である。リーダーの最初のフレーム（例外のときの `finally` を含む）と、Layout.astro の 10 秒の fallback。
   - JavaScript がないときは何も付かない（HTML に `aria-hidden` は書かない）。CSS に `aria-hidden` のセレクターはないので、付け外しでスタイル計算は起きない。トレースでも、最初のフレームのスタイル計算は 0〜1 ms だった。

待機中もスクロールポートは `tabindex="0"` のままフォーカスできる。`visibility: hidden` のときはフォーカスできなかった。待機は通常 1 フレームから数百 ms なので、そのままにした。

`scripts/measure-article-open.mjs` に `painted` を加えた。`visible` は `rm-pending` を外した時点で、リーダーの最初のフレームの中にある。そのフレームのスタイル計算、レイアウト、描画はどの区間にも入っていなかった。`visible` の時点で投げたタスクが動いた時刻を `painted` とし、トレースに `visible→painted` と、その後の 500 ms（`painted→end`）の区間を加えた。

### 確認

`tests/reading-initial-paint.browser.test.mjs` は、本文の計算値の `visibility === 'hidden'` を確かめていた。これを、リーダーの最初のフレームより前のすべてのフレームで、計算値の `clip-path` が `inset(50%)` であること、画面中央のヒットテストが本文に当たらないこと、`aria-hidden="true"` であることに改めた。一覧からの遷移と直接の読み込みの両方で、1 段、n段、保存なしの 3 通りを調べる。従来はn段以外のフレームを調べていなかったが、すべてのモードで調べるようにした。表示後は `clip-path: none`、`aria-hidden` なし、中央が本文に当たることを確かめる。JavaScript なしでは `clip-path: none` で `aria-hidden` もないこと、fallback では `aria-hidden` が付いてから外れること（MutationObserver の古い値が `[null, 'true']`）も確かめる。main のビルドでは両エンジンで失敗する。`reading-ordinary-navigation.browser.test.mjs` の `visibility` の比較も `clip-path` と `aria-hidden` に改めた。

## 記事を直接開いたときの数式フォントの到着（2026-11-09、PR #24）

この節は段組みへの改名（PR #27）の後に書いたので、現在の名前を使う。

Lighthouseで `symmetric-polynomial` をn段で直接開くと、点数は73、TBTは450 msだった。この記事の要素数は13,386で、大半はMathJax CHTMLの `mjx-*` 要素である。記事全体のレイアウトは、CPUを遅くしない条件でも1回40〜200 msかかる。

原因は数式フォントの届き方だった。preloadしていたのは `mjx-tex-n` だけで、ほかのフォント（`zero`、`brk`、`so`、`lo`、`s3`、`s4`）は最初のレイアウトの途中で初めて要求される。これらはそのレイアウトの後に届き、届くたびに記事全体をレイアウトし直していた。

変更は次の2つ。

- `src/pages/[slug].astro` で、記事が使う数式フォント（`mathFontFaces()` の結果）をすべてpreloadする。一覧でホバーしたときの先読みが、読み込み済みのフォントのpreloadを遷移前に取り除く処理は、これまでどおりURLごとに働く。`tests/math-fonts.browser.test.mjs` は、直接開いた数式記事でpreloadしたフォントと実際に要求されたフォントが一致することを、1段・n段で確かめる。
- n段の準備中（`cl-premount`）は、目次が `astro:page-load` で見出しの位置を読まない（`src/components/Toc.astro`）。1段で始めるときは、段組みが本文を段から戻すとき（`releasePremounted()`）と10秒後の退避のときに `cl:single` を送り、目次はそこで現在の見出しを合わせる。

CPUを4倍遅く、回線を遅延40 ms・10 Mbpsにして直接開き、変更前後を交互に8回ずつ測った中央値（ms）。GitHub Pagesと同じくgzipで配信した。`python -m http.server` は圧縮せずに約464 KBのHTMLを送るので、FCPと帯域の条件が変わり、比較に使えない。

| | 変更前 | 変更後 |
| --- | --- | --- |
| n段のTBT | 474 | 132 |
| n段の長いタスクの合計 | 1689 | 1309 |
| 1段のTBT | 199 | 0 |

Lighthouse 13.6（デスクトップ設定でCPUを4倍遅く、n段、6回ずつ）では、点数の中央値が約78から約88に上がった。変更前は、フォントが遅れて届いた回に記事の表示前の描画が先に行われ、CLSが0.624になることがあった。変更後は一度も出なかった。デプロイ後に本番の同じページを測ると、点数は73から95になった（FCP 0.5 s、LCP 0.6 s、TBT 150 ms、SI 1.3 s、CLS 0.006）。TBTとSIはデスクトップの良好の境界（150 ms、約1.3 s）にある。Lighthouseのシミュレーションと実際に遅くした計測は値が食い違うので、両方を見る。

目次の変更だけを外した版とも比べた。数式フォントをpreloadした後では、長いタスクの合計は1299 msと1315 msで、差は出なかった。目次が位置を読む前にフォントが届いたときだけ、記事全体のレイアウトを1回減らす。通常の読み込みで害がないので残した。

Nunitoのpreloadも試したが採らなかった。レイアウトの回数は減らず、FCPが30〜80 ms遅れた。

この変更の後、`document.fonts.ready` が早く解決するようになり、段組みの開始前に操作するブラウザー試験がCIで失敗するようになった。`cl-ready` は段組みの最初のフレームがモードを適用する前に付く。試験は `html.cl-ready:not(.cl-pending)` を待つように直した（`math-fonts.browser.test.mjs` はPR #24の16ef251、ほかの22か所はPR #25）。PR #28 からは `tests/browser.mjs` の `waitForColumnLayout` がこの待ちをまとめている。
